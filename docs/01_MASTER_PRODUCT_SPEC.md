# 01 — MASTER PRODUCT SPEC

## 1. Назначение документа

Этот файл — главный product source of truth для демо MVP логистической платформы.

Если другие документы противоречат этому файлу, приоритет у:
1. `01_MASTER_PRODUCT_SPEC.md`
2. более специализированного файла по конкретной теме
3. текущей реализации только если она явно подтверждена документацией

Цель MVP — показать сквозной рабочий сценарий логистической компании с собственным складом, несколькими типами пользователей и единой сущностью «Заявка».

## 2. Что за продукт

Web-платформа для управления логистикой и складскими операциями.

Система объединяет:
- заказчиков;
- менеджеров / логистов;
- водителей;
- сотрудников склада;
- администраторов.

Главный принцип:
> все роли работают не в разрозненных системах, а вокруг одной заявки и одной истории событий.

## 3. Основная сущность

Центр продукта — `Order` / «Заявка».

Заявка может включать:
- клиента;
- компанию клиента;
- поставщика;
- одну или несколько точек забора;
- груз;
- одну или несколько услуг;
- склад;
- водителя;
- транспорт;
- документы;
- вложения;
- стоимость;
- текущий статус;
- историю статусов;
- комментарии;
- уведомления.

## 4. Основные пользовательские роли

### Client
Заказчик:
- создаёт заявки;
- отслеживает статусы;
- прикладывает документы;
- видит фото и историю;
- получает итоговые документы;
- управляет профилем компании.

### Manager
Менеджер / логист:
- видит все заявки;
- проверяет входящие заявки;
- уточняет данные;
- рассчитывает стоимость;
- назначает водителя и транспорт;
- управляет маршрутами;
- контролирует прохождение заявки;
- решает исключения и проблемы.

### Driver
Водитель:
- работает преимущественно с мобильного;
- видит только назначенные ему задания;
- получает адреса, контакты, данные груза;
- меняет статусы исполнения;
- загружает фото и подтверждения.

### Warehouse
Сотрудник склада:
- видит ожидаемые поступления;
- принимает и выдаёт груз;
- фиксирует фактический вес / количество мест;
- выполняет и отмечает складские операции;
- загружает фото;
- переводит груз по складским статусам.

### Admin
Администратор:
- управляет пользователями и ролями;
- управляет компаниями;
- управляет услугами и справочниками;
- имеет доступ ко всем данным;
- видит журнал действий;
- управляет demo settings.

## 5. Цель Demo MVP

MVP должен не имитировать продукт статическими экранами, а демонстрировать рабочую систему.

Обязательные свойства:
- реальная тестовая БД;
- реальные CRUD-операции;
- переключение ролей;
- role-aware UI;
- единая заявка, которую разные роли видят по-разному;
- реальный lifecycle статусов;
- загрузка mock-файлов / изображений;
- demo seed;
- responsive / mobile-first интерфейс;
- возможность развернуть проект на Vercel.

## 6. Главные demo-сценарии

### Scenario A — клиент создаёт заявку
1. Client входит в систему.
2. Создаёт заявку.
3. Указывает поставщика.
4. Добавляет груз.
5. Выбирает услугу.
6. Прикладывает документ.
7. Отправляет заявку.
8. Заявка получает статус `SUBMITTED`.

### Scenario B — менеджер принимает заявку
1. Manager открывает входящую заявку.
2. Проверяет данные.
3. Уточняет стоимость.
4. Назначает водителя и транспорт.
5. Переводит заявку в `CONFIRMED` / `DRIVER_ASSIGNED`.

### Scenario C — водитель выполняет забор
1. Driver видит новое задание.
2. Нажимает «Принял».
3. Меняет статусы по ходу поездки.
4. На погрузке добавляет фото.
5. Подтверждает забор.
6. Груз направляется на склад или к получателю.

### Scenario D — склад принимает груз
1. Warehouse видит ожидаемый груз.
2. Сверяет номер заявки.
3. Фиксирует фактические параметры.
4. Добавляет фото.
5. Отмечает дополнительные операции.
6. Переводит заявку дальше по lifecycle.

### Scenario E — клиент отслеживает результат
1. Client видит timeline.
2. Получает актуальный статус.
3. Видит фото.
4. Видит документы.
5. После завершения заявка получает `COMPLETED`.

## 7. Типы заявок MVP

Обязательные:
- `PICKUP_TO_WAREHOUSE` — забрать груз и привезти на склад;
- `WAREHOUSE_INTAKE` — принять груз непосредственно на склад;
- `DELIVERY_OWN_TRANSPORT` — доставить своим транспортом;
- `DELIVERY_TRANSPORT_COMPANY` — передать в стороннюю транспортную компанию;
- `COURIER_DOCUMENTS` — доставка документов / небольшой курьерский сценарий;
- `WAREHOUSE_SERVICE` — складская операция без полноценной перевозки.

В UI они могут называться на русском.

## 8. Дополнительные услуги MVP

Поддержать как selectable services:
- хранение;
- погрузка;
- разгрузка;
- упаковка;
- маркировка;
- резка / обработка;
- фотоотчёт;
- страхование;
- доставка документов;
- экспедирование.

Не каждая услуга обязана иметь сложную бизнес-логику в первой версии. В MVP достаточно:
- выбрать услугу;
- сохранить её;
- показать её во всех релевантных ролях;
- отразить в стоимости / деталях заявки.

## 10. Что не входит в Demo MVP

Не реализовывать без отдельного документа:
- реальную интеграцию с 1С;
- ЭДО / Диадок / СБИС;
- онлайн-эквайринг;
- реальный GPS-трекинг автомобиля;
- сложный оптимизатор маршрутов;
- полноценную WMS с адресным хранением;
- QR / штрихкоды;
- юридически значимую электронную подпись;
- production-grade Telegram bot;
- нативные iOS / Android приложения;
- сложный тарифный движок.

Для будущих интеграций архитектура должна оставаться расширяемой.

## 11. Demo Role Switcher

В demo build должен существовать быстрый переключатель ролей.

Роли:
- Client;
- Manager;
- Driver;
- Warehouse;
- Admin.

При переключении:
- меняется активный demo user;
- меняется навигация;
- меняются доступные действия;
- данные остаются общими;
- одна и та же заявка должна быть доступна разным ролям согласно permission rules.

Switcher — demo-инструмент, а не часть production UX.

## 12. Основные критерии готовности MVP

MVP считается готовым, когда:
- [ ] проект запускается локально одной понятной командой;
- [ ] создана и мигрирована БД;
- [ ] seed создаёт полноценный demo dataset;
- [ ] доступны все 5 ролей;
- [ ] role switcher работает;
- [ ] Client может создать заявку;
- [ ] Manager может обработать заявку;
- [ ] Driver может выполнить назначенные действия;
- [ ] Warehouse может принять / обработать груз;
- [ ] Admin видит справочники и пользователей;
- [ ] timeline заявки обновляется;
- [ ] статусы валидируются;
- [ ] документы / вложения отображаются;
- [ ] интерфейс работает на mobile и desktop;
- [ ] нет критического горизонтального overflow;
- [ ] TypeScript strict проходит без ошибок;
- [ ] production build проходит;
- [ ] demo можно развернуть на Vercel.

## 13. Главный принцип продукта

Любая новая функция должна отвечать на вопрос:
> помогает ли она одной из ролей быстрее и понятнее провести заявку через реальный логистический процесс?

Если нет — для Demo MVP её не добавлять.
