# 12 — MANAGER WORKFLOWS

## 1. Роль

Manager / Logistician — главный оператор системы.

Главная задача:
> быстро превратить входящую заявку клиента в исполнимый логистический процесс и довести её до завершения.

Показать:

- без водителя;
- сегодня на забор;
- сегодня на доставку;
- на складе;

- завершено сегодня;
- на складе;
- issue count.

Не перегружать аналитикой.

---

## 4. Входящая заявка

Manager открывает `SUBMITTED`.

Проверяет:
- клиента;
- поставщика;
- маршрут;
- груз;
- документы;
- услуги;
- даты;
- комментарии.

Действия:
- принять в работу;
- запросить уточнение;
- поставить на hold;
- отменить по правилам;
- добавить внутренний комментарий.

Переход:
`SUBMITTED -> REVIEW`.

---

## 5. Согласование

На этапе `REVIEW` Manager:
- уточняет данные;
- задаёт стоимость;
- подтверждает выбранные услуги;
- выбирает склад;
- планирует даты;
- при необходимости корректирует route points.

После проверки:
`REVIEW -> CONFIRMED`.

---

## 6. Назначение водителя

Manager выбирает:
- Driver;
- Vehicle;
- planned pickup;
- route.

После назначения:
`CONFIRMED -> DRIVER_ASSIGNED`.

Проверить:
- водитель активен;
- транспорт активен;
- нет очевидного конфликта назначения, если basic conflict check реализован.

Для Demo MVP сложный календарь ресурсов не обязателен.

Для заявок, прошедших через склад, при статусе `READY_FOR_DELIVERY` менеджер отдельно подтверждает исходящих водителя и автомобиль. Это нужно и для приёма груза прямо на склад, когда у заявки ещё нет водителя. Статус при назначении не меняется: после оформления складом операции `RELEASE` водитель начинает `DELIVERY_IN_PROGRESS`.

## 8. Operational controls

Manager может:
- сменить разрешённый статус;
- назначить / заменить driver;
- назначить vehicle;
- изменить planned date;
- добавить service;
- изменить service price;
- добавить internal note;
- добавить client-visible note;
- загрузить document;
- отметить issue;
- снять issue / hold.

Все значимые действия пишутся в audit.

---

## 9. Issue workflow

При проблеме:
- выбрать / написать причину;
- `status -> ISSUE`;
- сохранить предыдущий operational status в истории / контексте;
- уведомить релевантных пользователей.

Примеры:
- груз не готов;
- не совпал вес;
- нет документов;
- клиент недоступен;
- повреждение;
- невозможна доставка.

После решения Manager выбирает валидный возвратный status.

## 10. Планирование

Для Demo MVP достаточно простой страницы:

### Today
- pickups;
- deliveries;
- warehouse arrivals.

### Unassigned
- confirmed orders without driver.

### Driver load
- список водителей;
- текущие назначения.

Не строить полноценный Gantt / route optimization.

## 11. Bulk actions

В первой версии не обязательны.

Если реализуются:
- не разрешать массово менять lifecycle без проверки каждой заявки;
- bulk export допустим;
- bulk assign — только если безопасно.

---

## 13. Internal vs client-visible

Manager всегда должен понимать scope комментария.

UI:
- переключатель / label:
  - «Внутренний»
  - «Виден клиенту»

По умолчанию внутренний комментарий не должен случайно стать публичным.

---

## 14. Desktop priority

Manager — главный desktop-heavy пользователь.

Приоритет:
- плотная информация;
- быстрые фильтры;
- быстрые действия;
- split view допустим;
- таблицы допустимы.

Mobile:
- просмотр и базовые urgent actions;
- не пытаться повторить весь desktop UX один в один.
